# MathPath v0.5 评测计划与结果报告模板

本轮交付的是可运行的采集、匿名人工评审、汇总流程，以及尚未填写的材料。没有把程序检查数量、模拟状态或空评分表当作真实学习成绩，也没有填造真实受试者反馈。任何真实请求与人工评分都必须在报告中另行注明执行时间、请求配置模型、完整分母和审阅者人数。

## 为什么分别评构图、教学决策和真实使用

MathDial 研究区分数学解题与教学引导，并检查错误反馈、过早透露答案等问题；这支持我们把解释、教学动作与检验问题单独评审，而非仅检查模型能否写出最终答案。[MathDial 原论文](https://aclanthology.org/2023.findings-emnlp.372/)

LLM 评审研究讨论位置、冗长度和自偏好等偏差。因此本工具使用固定共同任务、条件顺序随机化与人工证据，不将模型评分作为正确性真值。这是根据研究采取的设计选择，并非上述论文验证了 MathPath。[Judging LLM-as-a-Judge 原论文](https://arxiv.org/abs/2306.05685)

| 层次 | 输入与输出 | 可以支持的结论 | 仍不能支持的结论 |
|---|---|---|---|
| 数学构图 | 20 个目标，生成节点/AND-OR 依赖/诊断任务 | 当前模型在这些目标上的格式成功率及人工数学核查结果 | 学习提升、所有数学主题可靠 |
| 同模型教学决策 A/B | 两条件均有目标/困惑/完整自报状态，B 多审核图与人工映射 | 审核结构上下文对当次教学决策评分的描述性差异 | 自动构图质量、软件整体效益、长期学习提升 |
| 真实试用 | 至少 3 名真人完成目标、学习、提问、历史恢复流程 | 流程可用性、实际卡点、反馈后修复情况 | 小样本即可证明普遍提高成绩 |

A/B 的处理差异是“审核结构上下文（含图的数学约定）+人工状态映射”：共同输入未单独包含 `math_context`，而 B 的审核图可以包含它。因此结果不能解释为图拓扑或依赖边本身的净效果，也可能反映补充数学假设与人工知识整理的作用。

## 先固定试验，再采集

1. 从 20 个目标、40 个模拟状态中确定选集；标注哪些案例参与过开发。保留从真实问题得到且未用于提示词调整的后续保留集，禁止把当前开发集称作独立 benchmark。
2. 人工按教材核查图，记录目标、教学先修、OR 替代路线的假设。对每个自报状态人工映射已知节点，并记录不能可靠映射的概念。不能确定时先改图或排除案例并说明原因，不能自动猜标签。
3. 固定共用指令、输出 Schema、同一模型配置、选集、试次和顺序种子。一个目标两个状态、两个条件、3 次需要 12 次请求；全量 20/40 需要 240 次。按量计费或订阅额度与当前服务有关，本工具只估计请求数量，不估算未知的人民币费用。
4. 收集每次成功或失败；保留全部原始结构化决策与精确输入。记录模型名是请求配置 ID，不能据此验证代理服务内部具体模型版本。
5. 由协调者创建匿名材料与独立解盲表。审阅者不看模型/条件标签；输出措辞可能破盲，报告这一限制。至少一名能核查相应数学的审阅者；若两名，先独立评分，保留分歧与证据后再讨论，不覆盖原分。
6. 使用六个决策维度 0–2 分；允许替代解法和其他合理教学动作。每个非空分数须有审阅者与定位证据。数学错误逐条列出，不能用其他项目的高分抵消。
7. 以同一案例/状态/试次/审阅者配对 A/B；缺失不补零，失败不剔除。报告每个分母、均分分布、平分与负差；小样本不使用未经支持的显著性或学习提升结论。

## 人工评分报告

以下内容是模板，需填写真实输出与人工证据后使用。

- 版本与采集日期：待执行。
- 请求配置模型/服务类型/请求格式/输出格式：待执行。
- 数据集、映射、指令和 Schema 哈希：采集清单自动保存。
- 选定目标/状态/试次、计划请求数：待选择。
- 已记录请求/缺失计划请求/成功输出/失败请求：采集与摘要自动计数。
- 审阅者数量及相关数学背景：待真实填写，不记录姓名、邮箱或账号。
- 各条件、各维度有效评分数与 0/1/2 分布：待人工填写后汇总。
- 同一审阅者完整配对数、B-A 均值、A 较好/B 较好/平分数量：待汇总；不完整项不配对。
- 发现的数学错误、错误位置、核查教材、修复措施：待真实填写。
- 排除规则、未评输出与缺失原因：逐项记录。
- 局限：开发集、自报状态、审阅图、匿名措辞泄漏、小样本、模型路由不可见；没有测量真实学习提升。

CSV 和 JSON 均支持保留具体人类审阅证据。摘要中数学错误总数按审阅标注计算；多位审阅者可能指出同一错误，不能把总数直接当作独立错误数。可进一步由协调者建立错误去重表，但须保留原始评分。

## 至少 3 名真人试用

使用 `user-feedback-template.csv` 和 `project-evaluation.md` 中的流程。受试者自己操作软件，分别输入目标、选择细分方向、查看先修、学习一张卡、做一道题、追问、保存未解决问题、切换项目并恢复历史。记录成功与失败、耗时、卡点和具体意见；问“为什么卡住”比仅问满意度更有用。

P01/P02/P03 只是空代号，没有对应已完成受试者。学习轨迹、备份和对话属于个人内容，分享前由参与者确认并移除身份信息；无需收集账号或密钥。课程所需反馈和根据反馈的优化仍待真实执行。若只做可用性测试，在答辩中如实说明；要测学习效果，另需独立题目、前后测与更合适的对照设计。

## 交付与现场 Demo

GitHub 仓库包含代码、运行说明、固定案例、工具、评测计划、经过匿名化的真实结果和局限。配置与凭证不入库，采集结果默认在忽略目录；发布结果前单独检查，不能把忽略规则当作内容审核。

Demo 可按“目标细分 → 学习地图 → 教学卡与练习 → 悬浮追问 → 未解决问题 → 项目与历史恢复”展开，再展示真实评估的失败案例和修复。网络失败时使用明确标记的离线审核样例，不能将离线内容冒充现场模型回答。GitHub 发布、外部部署和联系试用者都须另行执行，本评测工具不会自动发布或发送信息。
