# MathPath 数学内容与教学决策评测（v0.5）

这里准备了 **20 个数学目标、40 个模拟自报状态**：线性代数、基础群论、同调、拓扑各 5 个目标。案例由人工编写，用于发现错误和比较后续版本；不是经过独立专家标定的基准，也没有证明 MathPath 能提高学习效果。

每个案例包含当前困惑、必要概念核查要点、具体错误陷阱、两个不同知识状态，以及可接受的第一步示例。`expected_concepts` 不要求一概念对应一个节点；同义描述、合并节点、其他合理解释与不同学习路线都可以接受。`acceptable_first_steps` 也不是穷尽答案。当前数据集不规定唯一“标准图”。

## 先离线查看

在解压后的 MathPath 项目根目录中打开 Windows PowerShell，执行：

```powershell
.\.venv\Scripts\python.exe -B evals\run.py
.\.venv\Scripts\python.exe -B evals\run.py --list
```

默认行为只是检查案例结构、ID、来源引用、自报状态和评分档位，**不会导入模型调用模块，也不会读取登录记录或联网**。它能证明材料格式可用，不能证明数学答案正确或教学有效。默认校验也可用普通 Python 运行，不依赖第三方包。

准备一个可填写的离线评审材料包：

```powershell
.\.venv\Scripts\python.exe -B evals\run.py --prepare
```

材料包保存到 `evals\results`，包含全部案例、固定构图输入和空评分表。也可用 `--case homology_quotient` 只准备一个案例。分数 `null` 表示未评，不能当作 0 分。

## 显式采集模型输出

下面的命令会使用 MathPath 已配置的真实模型和账号额度；本轮开发没有运行这些命令：

```powershell
.\.venv\Scripts\python.exe -B evals\run.py --run --case homology_quotient --trials 1
```

确认单个案例的请求和结果适合评审后，再选择需要的案例。重复 `--case` 可选多个目标；`--case all --trials 3` 会发起 60 次真实构图请求。`--run` 不指定 `--case` 会被拒绝，避免误触全量调用。

图采集器使用生产端构图指令和结构模型，一次读取当前模型配置快照后进行请求；构图输入固定为“学习目标 + 当前困惑”。**它不会把模拟状态传给无状态构图器**，也不会假装已经完成状态适配实验。每个结果附有：

- 案例 ID、试次、UTC 时间、实际请求配置中的模型 ID 和服务类型；这个 ID 不是代理服务内部模型路由的证明；
- 数据集、输入、构图指令及 JSON Schema 的 SHA-256；
- 通过生产端结构校验的图，或请求失败的异常类型；
- 空的人工数学评分表和每个状态的推荐评审表。

结果逐次写入 JSONL 并刷新到磁盘。失败也保留为一条记录；异常正文、认证信息和原始响应体不写入结果。`evals/results/.gitignore` 排除采集结果，源码备份应同样排除该目录内的 JSON/JSONL。默认没有自动模型评分器，没有图 ID 的逐字匹配评分。

v0.4 的图可附带 `study_plan`（模式、可检验目标、共同数学约定、诊断、最终检验、出处）以及节点的先修理由、所需能力和分支结果。旧图可以省略这些字段，不应仅因省略新元数据就判为结构无效。评审时另检查新元数据是否与节点、任务和数学条件一致；默认填充或结构校验通过不代表这些条件已经被专家认可。

当前采集工具没有自动采集完整的 v0.4 学习过程，也不会自动完成作答、调用反馈模型、邀请用户或填写试用结果。需要明确记录使用的模式与版本；要比较模式或学习反馈，应按下文固定方案另行收集完整输入和输出。

## 人工评分方法

`cases.json` 中有六个维度，各 0–2 分：必要概念覆盖、数学正确性、教学依赖合理性、OR 分支合理性、目标匹配、状态适配。每个分数必须注明对应节点、边或教学内容的证据。数学正确性重点查看每例的 `pitfalls`；评分要考虑目标所需的条件，而不是要求每张小图展开整个教材。

没有 OR 分支不是错误。如果一个 AND 路线已足够、没有合理的替代路线，OR 维度应得 2 分。存在 OR 时，要检查每个分支能否独立支撑后续节点，不能因展示了多条路线就加分。

图采集阶段只评前五项。状态适配要另行运行节点推荐和教学输出后才能评分：审阅者首先将该次图的节点 ID 映射到案例中的自报概念；不同图可能使用不同 ID，不能直接字符串匹配或自动把“听过”当作“掌握”。如果节点范围过大而无法可靠映射，记录这种不确定性，避免强行勾选。

程序校验通过只说明引用、格式和 DAG 等结构有效，不能代替数学及教学审阅。请求失败应计入失败率；不要删掉失败试次再只报告成功平均分。实质数学错误另行计数，不能被其他维度的高分掩盖。

## 已可运行的同模型 A/B 比较

先用这些案例做开发检查，修正评分歧义，再从真实学习问题中补充独立保留集。当前 20 个案例可能参与提示词调整，因此最终结果不能把它们称为从未见过的测试集。

`compare.py` 已实现两个教学决策条件：A 收到目标、困惑和完整自报状态；B 收到相同内容，加上已审核的 AND/OR 图和人工已知节点映射。两者使用同一份不可变模型配置、相同指令和输出结构。没有自动字符串匹配掌握情况，也没有模型给自己评分。这是“人工审核结构上下文”的比较，并不直接检验自动构图或整个软件是否提高学习成绩。

离线准备完整的 20 个目标、40 个状态与 80 行空评分计划：

```powershell
.\.venv\Scripts\python.exe -B evals\compare.py --prepare --out evals\results\prepare
```

在 `reviewed-mapping-template.json` 中为每个选定案例放入人工核查过的 `reviewed_graph`，为其全部状态填写 `known_node_ids`。图可保留先修理由、能力要求和共同数学约定；须移除 `study_plan.diagnostics` 和 `study_plan.final_tasks` 中的题目/答案（改为空列表或省略），避免 B 同时多获得已解例题。图审批 `graph_approval` 和每个状态的 `mapping_approval` 都须填写 `approved: true`、匿名审阅者代号 `reviewer` 和具体 `evidence`。空映射可表示确实没有对应已知节点；也须人工批准。默认模板全部未批准，禁止直接运行。不能把待审核的模型图或自动标签匹配结果当作真值。

下面明确请求一个目标的两个状态、两个条件、每条件 3 次：**12 次真实模型请求**。本工具不会自动重试失败请求。

```powershell
.\.venv\Scripts\python.exe -B evals\compare.py --run --mapping evals\results\prepare\reviewed-mapping-template.json --case homology_quotient --trials 3 --out evals\results\pilot
```

重复 `--case` 可指定多个目标。全部 20 个目标、40 个状态、3 次试验会发起 **240 次请求**；工具在首次请求前打印数量和实际请求配置模型。`--run` 缺少明确的 `--case` 或人工批准映射时会被拒绝。离线入口不导入模型、账号或配置模块。共同任务的完整文本、Schema、输入、数据集和映射哈希逐条保留，配置中只保留模型名、服务类型、请求格式、输出格式，不保存密钥、地址或账号。

```text
共同任务：针对学习者当前困惑，选择一个下一步概念和教学动作。
请说明选择理由，给出一项简短理解检查；避免重复明确已掌握的内容。
教学动作从 formal_definition, geometric_intuition, concrete_example,
counterexample, analogy, proof_idea, prerequisite_review, micro_exercise 中选择。
共同输入：{goal, query, self_report, known_concepts, familiar_but_unclear_concepts}
A 额外输入：无。
B 额外输入：{reviewed_graph, manually_mapped_known_ids}。
共同输出：{focus_node_id:null或所给图中的ID, focus_concept, action,
          depth:0..3, rationale, explanation, check_question}。
```

采集后产生 `decision-collection.jsonl`。请求顺序在每个状态/试次内随机打乱 A/B，种子写入清单；中断后已经保存的行仍可检查，计划但尚未请求的项单列为缺失，不能算作失败或成功。输出必须通过共同格式校验；失败行只保留异常类型，不记录错误正文、认证信息或原始响应。

准备匿名人工评审材料：

```powershell
.\.venv\Scripts\python.exe -B evals\compare.py --blind evals\results\pilot\decision-collection.jsonl --out evals\results\blind
```

把 `anonymous-review.json` 或 `anonymous-scores.csv` 交给审阅者，**另行保管 `unblinding-key.json`**。评审副本隐藏条件、模型和能够直接泄露条件的节点 ID，并打乱编号；答案措辞仍可能让审阅者猜到条件，因此只称为匿名评审，不宣称绝对盲法。两种条件的评审者都能看到相同核查要点、可接受步骤和人工审核图。评分允许其他合理路线。

教学决策评审使用六个 0–2 分维度：数学正确性、目标匹配、先修与状态匹配、教学动作匹配、解释质量、检验问题质量。它们与上面用于**构图**的六维评分不同，不能混为同一结果。每项人工评分保留 `annotator` 代号与 `evidence`；缺失分数填 `null` 或 CSV 空格，不填 0。数学错误另填 `mathematical_error_count` 和逐项 `mathematical_errors`；声明 0 个错误时列表为空。

CSV 中 `evidence` 和 `mathematical_errors` 单元格使用 JSON 数组，例如 `["解释中把非零链误认为非零同调类"]`。也可直接编辑 JSON 的 `review` 对象。不要修改匿名材料中的问题、响应和数学参考。CSV 允许同一输出由多个匿名审阅者各填一行；重复的同一输出/同一审阅者会被拒绝。

汇总人工评分：

```powershell
.\.venv\Scripts\python.exe -B evals\compare.py --summarize evals\results\pilot\decision-collection.jsonl --reviews evals\results\blind\anonymous-review.json --key evals\results\blind\unblinding-key.json --out evals\results\summary
```

`human-review-summary.json` 报告每个条件的计划/记录/缺失请求、失败率的实际分母、未评输出数、各维度有效评分数量与分布、数学错误标注数量，以及同一目标/状态/试次/**同一审阅者**的完整 A/B 配对差。缺任一条件或任一分数的项不参与该维度配对；平分保留为平分。空评审表的均分和差值保持 `null`。多个审阅者可能重复指出同一错误，因此报告的是标注数量而非唯一错误数量。详细计划和报告结构见 [experiment-plan.md](experiment-plan.md)。

评审时给输出随机匿名编号并打乱顺序，隐藏 A/B 标签。审阅者先独立评分，出现分歧时保留原分及理由再讨论；如果只有一位审阅者，要明确报告这个限制。查看同一目标两种状态是否产生不同且合理的第一步，而非只检查它们是否匹配例示答案。报告各维度分布、实质数学错误率、请求失败率及状态间的差异；样本量不足时不做“显著改善”的结论。

上述比较检验的是推荐输出质量。若要声称提高实际学习，还需要独立的学习前后测、真实参与者及合适的对照设计，当前原型尚未完成这些工作。

## v0.4 学习流程评审与真实试用

沿用上面的 20 个目标和 40 个模拟状态检查内容，再把“目标 → 诊断 → 先修推荐 → 练习 → 反馈 → 下一步 → 历史恢复”作为独立的流程评审任务。建议逐项核对：

- 目标判准是否能检验用户的原始困惑，是否声明对象、系数、符号和适用条件。
- 诊断题能否区分主要卡点；允许跳过或“不确定”，不把猜对当作完全掌握。
- 先修所需能力是否符合当前模式；OR 分支是否达到同一种后续目标。
- 分级提示是否逐步帮助，补步骤和独立题是否形成合理过渡。
- 反馈是否评价实际推理、允许其他正确解法，并明确模型候选意见与本地参考的限制。
- 参考已展示、使用过提示或模型答案尚待核对时，记录是否保留相应标记，避免错误宣称独立通过。
- 下一步动作是否解决当前卡点，能否返回相关先修、重试、参考或独立检验。
- 题目快照、笔记、作答和反馈是否在历史恢复时保持一致；项目批删是否保留历史转未分类。
- v0.4.1 提问窗口能否围绕当前目标或知识点持续追问，第二轮是否正确承接前一轮，是否保留对象、系数和方向约定。记录模型与明确发送的输入快照；近期上下文最多 10 轮、60000 字符，不能把已省略的旧问题当作模型必然记住的内容。
- 问答回复的数学正确性、针对性和可操作性需要另行人工评审；本地参考模式只返回已有内容，不与真正生成的新问题回答混算质量分。候选回答、取消等待和保存失败不应被误计为已验证的学习进步。
- v0.4.2 本地细分是否仅在确实宽泛的输入触发，是否保留学习者想研究的方向，是否等待明确选择。覆盖规则有限，漏检和误检均需用真实输入另外统计；不把预设方向显示成功当作 NLP 目标识别已全面验证。
- 教材是否确实存在，作者和章节是否正确，是否符合当前数学对象与学习目标。核实目录的规则测试与推荐的教学适切性分别评审；未知主题诚实返回暂无推荐。
- 不确定或未答出的问题是否保留原问题与上下文，失败后的保存状态是否明确，用户能否搜索、手动确认解决及选择删除。问题计数可反映未解决卡点，但不能仅因标为解决就断言学生已经掌握。

这些是内容和交互核查项，不能仅以自动测试通过来填写数学评分。历史库中的学习记录、候选反馈和自报独立完成，也不自动成为学习效果数据；后测与延迟测验需要另行真实执行。

课程 Project 的试用步骤、指标和 Demo 建议见 [Project 评估与真实试用方案](project-evaluation.md)。[用户反馈表](user-feedback-template.csv) 预留 P01、P02、P03 匿名编号，其他列为空，必须由至少 3 名实际使用者的真实观察与意见填写。空表、模拟用户或开发者的自测不能计为 3 人试用；改进后应保留版本及复测证据。

软件回归检查使用项目根目录中的 `tests/run_offline.py` 和 `tests/frontend_v04.cjs`。前者是 Python 检查，后者需要 Node.js，并校验实际数学内容与 Python 学习状态契约，包括问答记录的真实 Python 往返校验。前端 DOM 模拟检查覆盖方向选择不自动生成、教材触发和缓存、问题记录与所选删除、拖动、调整大小、折叠、键盘、多轮记录、失败保留草稿、取消、切换历史隔离、100 轮上限和无历史临时对话。独立的真实 WebView2 窗口检查覆盖可见窗口拖动、调整大小、760×600 边界限制、折叠、弹窗切换、两轮本地问答、历史恢复及安全文本和公式排版；v0.4.2 另检查实际方向选择与取消、证明及自报能力触发教材、未解决问题的记录和手动状态操作。最终实际窗口检查的具体项目以发行报告为准，范围与 DOM 模拟检查分别报告。这些功能通过不代表模型已经给出了正确的数学回答。最终数量和发行测试结果见发行检查报告；离线、模拟、真实联网内容评审和真实用户试用应分别报告，不互相替代。
